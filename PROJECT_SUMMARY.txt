1. WHAT IS THE PROBLEM?
--------------------------------------------------------------------------------
Problem Name : Business Entity Resolution (Multi-Source Record Linkage)
Challenge    : AWS Machine Learning Challenge 2026

Goal:
We are given multiple business directories:
- Source 1 (S1) : Clean reference / canonical business records.
- Source 2 (S2) & Source 3 (S3) : Noisy secondary datasets with duplicate records,
  spelling variations, missing suffixes (e.g., Corp vs Corporation), and rearranged addresses.

Our job is to link each business in Source 1 with its exact matching records
in Source 2 and Source 3. If an S1 business has no match in S2 or S3, it is a
"singleton" and its match list must remain empty.


2. DATASET SIZES & ROW COUNTS
--------------------------------------------------------------------------------
TRAIN DATASET (Used for training & validation):
- train_source1.tsv      :  2,206,821 records (Reference entities)
- train_source2.tsv      :  5,034,616 records (Noisy secondary entities)
- train_source3.tsv      :  5,285,603 records (Noisy secondary entities)
- train_ground_truth.tsv :  2,206,821 records (True mapping S1 -> S2, S3)
  Total Train Records    : 12,527,040 rows

TEST DATASET (Used for final predictions):
- test_source1.tsv       :  1,732,544 records (Target S1 entities to match)
- test_source2.tsv       :  4,887,273 records (Candidate records)
- test_source3.tsv       :  5,082,316 records (Candidate records)
  Total Test Records     : 11,702,133 rows


3. WHAT ARE THE EXPECTED OUTPUTS?
--------------------------------------------------------------------------------
The pipeline generates two required .tsv files in the "output/" folder:

1) matching_results.tsv  (Main Leaderboard Submission)
   - Columns: source1_entity_id, matched_entity_ids
   - Row count: Exactly 1,732,544 rows (matches test_source1.tsv 1-to-1).
   - Format: Comma-separated IDs (e.g., S2-808920974,S3-285097097) or empty for singletons.

2) candidate_pairs.tsv   (Candidate Audit File)
   - Columns: source1_entity_id, candidate_entity_ids
   - Subset Rule: Every ID in matching_results.tsv MUST exist in candidate_pairs.tsv.


4. THE SOLUTION & MACHINE LEARNING MODELS
--------------------------------------------------------------------------------
Comparing 1.73M records against ~10M records directly would require trillions
of comparisons (impossible to compute). We solve this with a 2-stage architecture:

A. STAGE 1: CANDIDATE BLOCKER (Fast Pre-Filter)
   - Uses Lexical Prefix (first 4 letters) and Word Token Inverted Indexes.
   - Partitions by country (US, India, France, etc.) to keep RAM usage low.
   - Discards >99.8% of obvious non-matches.
   - Keeps only top-12 most likely candidate records per S1 entity.

B. STAGE 2: ML ENSEMBLE MODEL (50/50 LightGBM + XGBoost)
   - Features: Computes 20 similarity scores per candidate pair:
     * Name similarity (Levenshtein, Jaro-Winkler, token Jaccard, fuzzy ratios).
     * Address similarity (exact match, street number match, token overlap).
   - Models:
     * Model 1: LightGBM
     * Model 2: XGBoost
   - Final Prediction: Average probability = (0.5 * LightGBM) + (0.5 * XGBoost).
   - Decision Threshold: Set at 0.55.
     (Optimized for Macro F0.5 score, which penalizes false matches 2x heavier than misses).


5. HOW IT WORKS (STEP-BY-STEP WORKFLOW)
--------------------------------------------------------------------------------
Step 1: Text Cleaning & Normalization
        Lowercase, remove special punctuation, normalize business legal suffixes
        (Inc, LLC, Corp, Pvt Ltd) and address abbreviations (St, Rd, Ave).

Step 2: Country Partitioning & Streaming
        Processes records country by country in memory chunks to avoid RAM crashes.

Step 3: Lexical Candidate Search
        For each S1 record, quickly finds up to 12 potential matches in S2 and S3.

Step 4: Feature Calculation
        Calculates the 20 numerical similarity metrics using fast C++ rapidfuzz.

Step 5: ML Prediction & Thresholding
        LightGBM + XGBoost predict the match probability.
        If probability >= 0.55 -> marked as a TRUE MATCH.
        If probability < 0.55  -> rejected.
        If no candidate >= 0.55 -> marked as SINGLETON (empty output).

Step 6: Rule Validation
        Checks row count, header columns, ID format, and subset constraints.


6. FINAL RESULTS & PERFORMANCE
--------------------------------------------------------------------------------
- Evaluation Metric : Macro F0.5 Score (Precision-oriented).
- Validation Score  : ~0.842 F0.5 on held-out validation data (441,364 entities).
- Execution Safety  : 100% compliant with competition rules, zero format errors,
                      and constant RAM streaming.
